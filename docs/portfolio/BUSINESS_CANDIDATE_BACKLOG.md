## 1. Purpose

This document preserves every Business-scale idea discussed for AI Revenue Lab, including small spin-outs, related products, internal tools that may become products, and existing external projects that may later receive a Business number.

The backlog exists so ideas are not lost in conversation history or merged away merely because they resemble another product. A candidate may remain separate when its target user, result, buying decision, or primary use moment differs.

This document does **not** silently assign canonical numbers. A candidate becomes canonical only after the registry procedure is completed: explicit issue, duplicate/conflict review, product boundary, workspace decision, reviewed registry update, and supporting documentation.

New candidates follow the portfolio phase gates:

```text
product framing
→ UI visual design
→ UI approval
→ UX design
→ UX approval
→ backend authorization decision
→ backend implementation
```

During `UI_ONLY` mode, the backlog authorizes visual-reference planning only. It does not authorize UX or backend implementation.

## 2. Status vocabulary

- `canonical` — verified in the current Business Registry.
- `proposed-number` — a product decision or issue proposes the number, but the registry has not yet made it canonical.
- `candidate` — preserved product idea with no canonical number assignment.
- `existing-project` — a separate repository or deployed project exists, but it is not automatically a numbered Business.
- `spin-out` — extracted from a broader product or shared capability because it may have a distinct customer or result.

## 3. Portfolio thesis

Candidate selection is guided by the AI Revenue Lab thesis:

1. **Volume** — AI can produce more outputs than a human team can economically sustain.
2. **Speed** — AI can reduce production and response time from days or months to minutes or hours.
3. **Concurrency** — multiple Web and Local workers can research, create, verify, and operate in parallel.
4. **Real-time reaction** — current events and user feedback can change the next output quickly.
5. **Personalization** — each user can receive a different product edition rather than only a recommendation from a fixed catalog.
6. **Revenue evidence** — every implemented Business should eventually measure costs, engagement, and attributable revenue.

## 5. Relationship rule

Related products remain separate candidates when their primary output differs. Examples:

- Family Newspaper is related to Personal Edition, but it is collaborative and family-scoped.
- Language Learning Magazine is related to Living Learning, but its primary product is a recurring language publication rather than a general adaptive lesson flow.
- Local Shop Magazine is related to Neighbor Market, but it produces media for one shop rather than discovering nearby shops.
- AI Verification Engine is related to Korean AI Platform, but it can be sold or embedded as an independent approval and evidence component.
- Personal Memory Book and Personal Memory Novel use similar source material but produce fact-oriented and literary outputs respectively.
- Classic Literature Translation Studio and Personal Writing Voice Studio may interoperate, but the former owns source-accountable literary editions while the latter owns the consented personal-voice layer and its rights lifecycle.

Relationship is recorded as metadata; it is not a reason to erase the smaller idea.

## 6. UI-first execution

Every candidate selected for work follows:

- permanent umbrella Issue #154;
- `docs/operations/UI_UX_BACKEND_PHASE_GATES.md`;
- `docs/operations/NEW_BUSINESS_UI_FIRST_PLAYBOOK.md`;
- a separate product-decision issue;
- a separate Phase 1 UI-only issue;
- Web CTO direction, high-volume Web implementation, and risk-based Local visual validation.

The Phase 1 result is a polished visual reference using synthetic data and locally stored, documented assets. Minimal state switching is allowed only for visual review. It does not establish accepted UX, backend behavior, live data, authentication, persistence, or public launch.

After `UI_APPROVED`, a separate UX issue may be opened. Backend remains frozen until `UX_APPROVED` and explicit user authorization.

## 7. Promotion to the canonical registry

Before promoting any candidate:

1. search the registry, repository, issues, external project list, and aliases for conflicts;
2. define target user, product promise, primary result, and non-goals;
3. decide whether it is a new Business, a deployment of an existing Business, or a feature;
4. open a numbering/product-decision issue;
5. define the reference and product workspaces;
6. create and review the registry change through the repository’s normal review process;
7. update portfolio and app documentation;
8. preserve old aliases and migration consequences when renumbering.

Until these steps are complete, the number in this backlog is a working proposal only.
