이 문서는 두 방식의 차이를 나란히 놓아, 김범신 대표가 실제로 쓰는 ERP와 계약을
확정한 뒤 고를 수 있게 정리한 것이다. **어느 쪽이든 최종 선택은 고객 대표 확인
뒤에 내려간다.**

## 1. 확인 상태 표기 규칙

| 표기 | 뜻 |
|---|---|
| `확인` | 이카운트 공식 페이지에 그대로 적혀 있다 |
| `미검증` | 제3자 자료에만 있다. 참고용 |
| `미확정` | 어떤 공개 자료에서도 확인되지 않았다 |

## 2. 두 방식 개요

| 항목 | A안 — 엑셀 일괄등록 | B안 — Open API 품목등록 |
|---|---|---|
| 전달 방식 | 이카운트 화면의 **웹 자료올리기** 또는 **엑셀 자료올리기**로 파일 제출 | HTTP 요청으로 품목 등록 |
| 입력 규격 | 고객 계정에서 내려받는 **서식**의 열 이름·순서·필수 표시를 그대로 따라야 한다 | 요청 본문 필드 이름 |
| 공식 규격 공개 여부 | `미확정` — 고객 계정 안에서만 확인 가능 | `미확정` — 공식 매뉴얼이 로그인 뒤에만 제공됨 |
| 기존 자료 수정 | `확인` — 같은 방식으로 갱신할 수 있다 | `미확정` |
| 등록 건수 | `미확정` | `미확증` 300건 |
| 호출 제한 | 해당 없음 | `미검증` 10초당 1회 |
| 추가 비용 | 없음 | `확인` — API 사용에 추가 비용 없음 |
| 오류 확인 방식 | `확인` — 실패 사유를 즉시 확인할 수 있다 | `미검증` — 건별 성공·실패와 오류 목록 응답 |
| 사전 검증 | `확인` — API 테스트 기능이 있음 | `확인` — API 테스트 기능이 있음 |

## 3. 구현 난이도

| 관점 | A안 | B안 |
|---|---|---|
| 이 저장소에서 필요한 코드 | **이미 있음.** 정규화 결과를 서식 열에 맞춰 저장하면 끝이다. 서식 열 이름만 확정되면 된다 | **추가 코드 필요.** 인증(로그인·세션·ZONE)·요청 조립·응답 해석·건별 오류 매핑·재시도·레이트 제한 준수가 들어간다 |
| 처음 붙일 때 걸리는 일 | 서식 다운로드 → 열 이름 확인 → 매핑표 작성 → 저장 | API 계정·키 발급·매뉴얼 확보 → 요청 필드 매핑 → 인증 구현 → 샌드박스 검증 |
| 규격이 바뀌면 | 열 이름만 다시 맞춘다 | 필드 추가·변경을 코드로 반영해야 한다 |
| 오프라인 검증 가능성 | 높다. 파일을 만든 뒤 눈으로 확인 가능 | 낮다. 계정과 네트워크가 있어야 응답을 본다 |

이 저장소에서 이미 구현한 것은 A안 쪽에 가깝다.
`apps/erp-item-master/`는 정규화 결과를 프로파일 열 순서대로 저장하며,
`generic` 프로파일은 그대로 쓸 수 있고 `ecount_excel_template` 프로파일은
열 이름만 채워 넣으면 되는 상태다.

## 4. 실제 처리속도

측정은 **이 저장소의 파이프라인 기준**이며 이카운트 측 처리시간은 아니다.
이카운트 업로드 자체의 소요시간은 계정과 파일 크기에 따라 달라서, 공개 자료와
실측 어느 쪽으로도 이 시점의 수치를 말할 수 없다.

합성 30,000행 기준(2026-10-21, COM2 로컬):

| 단계 | 시간 | 비고 |
|---|---|---|
| 원본 읽기 | 0.4초 | CSV |
| 정규화 | 3.7초 | 필드 파싱·출처 기록 |
| 중복 탐지 | 2.8초 | 블록 처리 후 이름 비교 8,284쌍 |
| 검토 판정 | 0.4초 | |
| **파일 기록** | **32.4초** | **8개 시트 Excel 기록이 지배한다** |
| 합계 | **39.7초** | 초당 756행 |

파일 기록 단계의 대부분은 Excel 워크북 작성이다. ERP 이관에 실제로 필요한 파일은
CSV 한 장이므로, Excel 기록을 빼면 30,000행 기준 약 7.3초다.

이 측정으로 말할 수 있는 것:

- 정규화·중복·검토 단계는 3만 건 규모에서 10초 이내로 끝난다.
- 병목은 사람이 열어보는 검토 워크북이다. 이 파일은 선택 사항이며,
  CSV만 쓰면 병목이 사라진다.
- 이카운트 서버가 30,000건을 받아들이는지는 서버 제약이며, 이 측정으로 알 수 없다.

## 5. 대량 등록 적합성

| 관점 | A안 | B안 |
|---|---|---|
| 3만 건을 한 번에 | 서버가 받는다는 공식 정보가 `미확정`. 여러 파일로 나눌 수 있는지부터 확인이 필요하다 | 1회 300건 `미검증` 기준이면 100회 호출. 10초당 1회 제한 `미검증` 기준이면 최소 17분 |
| 중간 실패 | 파일 단위로 다시 올릴 수 있다 (`확인` — 실패 사유를 즉시 확인) | 건 단위 성공·실패가 응답에 있으므로 실패분만 다시 보낼 수 있다 (`미검증`) |
| 중간 결과 확인 | 올린 뒤 ERP 화면에서 확인 | 응답으로 확인 (`미검증`) |
| 기존 자료 갱신 | `확인` | `미확정` |

## 6. 오류 복구 방법

| 상황 | A안 | B안 |
|---|---|---|
| 어떤 행이 왜 실패했는지 | `확인` — 업로드 실패 사유를 즉시 확인 | `미검증` — 건별 오류 목록 |
| 부분 성공 처리 | 이카운트에서 성공분은 반영된 상태이므로 실패분만 정리해 다시 올린다 | 응답에 성공·실패 건수가 있으므로 실패분만 재전송한다 |
| 사람이 해야 하는 판단 | 같은 품목의 중복, 누락된 가격·규격 같은 **판단**은 두 방식 모두 동일하게 사람이 한다 | 동일 |
| 되돌리기 | 다운로드한 기존 자료를 다시 올리는 방식이 `확인` | `미확정` |

중요한 구분: **오류 복구의 "복구" 부분은 두 방식 모두 사람이 하는 일이다.**
사람이 확정해야 하는 대상은 값 자체(가격·규격·중복)와 같고, 방식이 달라진다고
사람의 판단량이 줄지는 않는다. 줄어드는 것은 사람이 값을 다시 입력하는 시간이다.

## 7. 권고 (확정 전 잠정)

**1차는 A안 엑셀 일괄등록을 권고한다.** 근거는 다음 세 가지다.

1. 이 저장소에 이미 있는 코드로 이어진다. 서식 열 이름만 확정하면 된다.
2. 규격을 고객이 직접 확인할 수 있다. 양식을 내려받아 열 이름을 확인하는 일이
   API 매뉴얼을 읽는 일보다 짧고, 그 과정에서 실제 운영 데이터 구조도 함께 알게 된다.
3. 오류 확인과 부분 재업로드가 공식 페이지에서 확인된 기능이다.

**B안 Open API는 2차 후보로 남긴다.** 계약을 확정하고 반복 등록·갱신이 실제
업무 주기가 되면 그때 검토한다. API는 "한 번 만들어 계속 돌리는" 방식이므로
일회성 대량 등록이 반복되지 않으면 도입 이유가 약하다.

이 권고는 **ERP가 이카운트라는 전제가 확정된 뒤에** 적용된다. 다른 ERP라면
A안의 양식 열 이름도 달라지고 B안의 인증 방식도 달라진다.

## 8. 두 방식 모두에 남는 공통 전제

어느 방식을 고르든 정규화 파이프라인과 검토 워크플로는 그대로 쓰인다.
ERP가 바뀌면 바뀌는 것은 **임포트 프로파일의 열 구성 하나**뿐이며,
그 구성의 근거 상태를 `erp_field_mapping_status.csv`가 계속 기록한다.
