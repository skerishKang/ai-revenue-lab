## 1. 검토 대상 아이디어

설치 프로그램(`padiem-pc-connect.exe`)이 Windows에 `padiem://` 프로토콜 핸들러를
등록하고, 웹 첫 화면이 `padiem://pair/...` 링크를 눌러 반응(창 포커스 이동·타임아웃)을
관찰해 "설치됨/미설치"를 판단한다. 미설치로 판단되면 기존 설치 모달을 연다.

## 2. 브라우저별 제약 (판정을 구조적으로 무너뜨리는 것들)

| 제약 | 내용 | 판정에 미치는 영향 |
|---|---|---|
| 등록 조회 API 없음 | JS는 OS에 등록된 핸들러 존재 여부를 물어볼 방법이 없다. `navigator.registerProtocolHandler`는 웹 쪽 등록(사용자 승인 필요)이지 설치 감지가 아니다 | "반응이 없다 = 미설치" 추론만 가능 |
| 확인 대화상자 | Chrome/Edge/Firefox는 외부 프로토콜 실행 전 확인창을 띄운다(항상 허용 저장 전까지) | 사용자가 취소하면 포커스 이동이 없다 → 미설치와 취소를 구분할 수 없다 |
| 타임아웃 오탐 | 반응 없음 판정은 임의 시간(예: 1.5초) 내 blur/visibility 변화 관찰인데, 백그라운드 창·절전·느린 PC·포커스 지연이 모두 "미설치"로 위장된다 | 거짓 음성 → 이미 설치된 PC에 설치 모달 재노출 |
| 자동 호출 제한 | 프로토콜 호출은 대체로 사용자 제스처를 요구한다 | 페이지 로드 시 자동 탐지 불가, 클릭 필요 |
| 임의 사이트 호출 | 어떤 웹 페이지든 `padiem://`를 부를 수 있다 | 핸들러에 토큰·권한을 실으면 악용 경로가 된다. 핸들러는 권한 없는 "열기"만 해야 한다 |
| 등록 시점 | 등록은 설치 프로그램의 관리자 권한 단계(HKCU\Software\Classes)에서 가능 | 첫 설치 전에는 당연히 미등록 → 첫 화면 판정에는 아무 정보가 없다 |

## 3. 대안 비교

**A안 — padiem:// 반응 감지(검토 대상)**: 브라우저 힌트로 설치 여부를 추정.
위 표의 오탐 구조(취소=미설치, 타임아웃=거짓 음성)를 피할 수 없고, 브라우저마다
동작이 달라 판정 기준을 못 세운다. 얻는 것은 "설치 모달을 건너뛸지" 하나뿐이다.

**B안 — 설치 후 에이전트가 서버에 알리고 웹은 관찰한다(현행, 채택)**: 설치
프로그램이 에이전트를 등록·실행하면 서버가 그 사실(계정 tag가 붙은 이름)을
관찰해 링크를 active로 만들고, 웹의 연결 흐름이 `/api/pc/pairings`를 몇 초마다
다시 읽어 새 PC가 보이는 순간 "연결됐어요 ✓ (이름)"을 말하고 스스로 닫힌다
(#6110으로 구현·병합). 판정이 결정적이고 브라우저 독립적이며, 권한 없는 세션
쿠키 하나로 끝난다. "이 브라우저가 설치를 시작한 PC" 구분은 웹이 내려준 tag가
새 링크로 나타나는지의 비교로 충분하다.

**C안 — 서버→브라우저 푸시(SSE/WS)**: B안의 폴링 간격을 없애는 개선이 될 수
있으나 신규 연결 인프라가 필요하다. 4초 폴링으로 체감 지연이 이미 수 초 내라면
필요성이 약하다. 별도 과제로 남긴다.

## 4. 결론

- 설치 **판정**은 브라우저 반응이 아니라 서버 관찰(B안)이 정답이다. 현행 구현을
  유지하고, padiem://를 설치 감지에 쓰지 않는다.
- padiem://가 남는 가치는 보조 진입뿐이다: 설치 파일 실행을 다시 안내하거나,
  설치된 프로그램을 포커스하는 딥링크 정도. 그 경우에도 (a) 핸들러는 토큰·권한을
  받지 않는다, (b) 웹은 padiem:// 호출 결과를 설치 판정 근거로 삼지 않는다,
  (c) 확인 대화상자는 기능으로 존중한다(임의 사이트 실행 방지).
- 구현은 하지 않는다. 이 메모는 이후 padiem:// 논의가 다시 뜰 때의 근거 문서다.
