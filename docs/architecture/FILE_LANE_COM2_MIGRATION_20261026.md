# 파일 레인(업로드·저장·파싱·대용량 결과)을 컴2 자체 서버로 이전 — Cloudflare 고정 한도 때문에 막히는 것들

추적 이슈: #5881. Owner 결정(2026-10-26). **설계이며 구현 완료를 뜻하지 않습니다.**

## 결정 (Owner, 2026-10-26)
파일 업로드와 대용량 파일 처리는 **최소한 컴2(자체 서버)로 옮긴다.** 나머지 서비스의 이전 여부와 무관하게 파일 레인만큼은 먼저 간다. 인증은 Cloudflare에 남긴다.

## ⚠️ 왜 — Cloudflare 경로의 고정 한도와, 그 때문에 못 하고 있는 것
코드에 박혀 있던 PADIEM 자체 제한은 #5872/#5875/#5877/#5862/#5876에서 걷어냈지만, 아래는 **코드로 못 넘는 물리 한도**다. 상수를 1GiB로 써도 실제 상한은 여기서 결정된다.

| 한도 | 값(플랜 기준) | 그래서 못 하는 것 |
|---|---|---|
| 요청 본문 크기 | 약 100MB | **100MB 넘는 PDF·문서 업로드가 엣지에서 413** — 1GiB 상수는 이름뿐 |
| Worker 메모리 | 128MB | 수십 MB XLSX/DOCX를 Worker 안에서 파싱(openpyxl 등) 불가 → OOM·1102. base64 첨부는 1.33배 더 먹음 |
| OOXML 전개 | 멤버당 32MiB 버퍼 상한을 둘 수밖에 없음 | 큰 워크시트 XML 한 장이 수백 MB면 깔끔한 거절이 아니라 크래시 |
| PC 파일 읽기 결과 | Worker가 결과 JSON을 통째로 버퍼 | 20MB까지만, 그 이상은 청크/컴2 경유 없이는 불가 |
| CPU 시간 | 요청당 CPU 상한(설정값 이내) | 600페이지 PDF 변환·대형 표 추출 같은 긴 처리는 중간에 끊김 |
| Python Worker(Pyodide) | 콜드스타트·패키지 크기 제한 | 네이티브 파서/변환기(poppler·libreoffice·OCR 등) 못 씀 |
| 응답 크기 | 버퍼링하면 메모리 한도 | 32MiB 넘는 렌더·미리보기·병합 결과 불가 |

결과: 사용자는 "우리 제한"이 아니라 **불투명한 엣지 오류(413·1102·502)** 를 본다. 이 한도가 PC 레인·문서 레인·견적 XLSX·PDF 변환 등 대부분의 기능 폭을 묶고 있다.

## 목표 상태
- 컴2에 파일 서비스: 업로드 수신(HTTPS, Cloudflare Tunnel) → 디스크 저장 → SHA-256 → 파싱/변환(실제 CPython·네이티브 도구) → **결과(텍스트·메타·미리보기)만** Chat/Engine으로.
- Chat Worker는 서명된 업로드 티켓만 발급하고 바이트는 만지지 않는다. 파일은 id(sha·크기·종류)로 참조한다.
- 업로드 상한 = 디스크(컴2 사양: NVMe 128GB(C 여유 33GB)·HDD 2TB). 상수 1GiB는 이 경로에서 실제 의미를 갖는다.
- PC 레인 읽기 결과(20MB+)·OOXML·PDF·XLSX 파싱도 같은 레인을 탄다.

## 단계
1. 컴2 파일 서비스(수신·저장·SHA·티켓 검증) + Tunnel. 2. 파서 이전(PDF/OOXML/XLSX/텍스트). 3. 첨부 참조를 id 기반으로 전환(브라우저 → 컴2 직접 업로드). 4. PC 읽기 결과 컴2 경유. 5. Worker 경로의 파일 처리 코드는 동결(새 기능 추가 금지), 이전 완료 후 제거.

## 비범위
인증·세션·과금은 Cloudflare 유지. 모델 호출 경로(B14)는 이 이슈와 무관.
