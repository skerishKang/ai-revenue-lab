# Engine D1 0012/0013 gated release and recovery

Scope: padiem-engine D1 only. This workflow is dispatch-only; do not invoke it until CTO explicitly directs apply. #6292 must be merged first. The run must target the exact current main 40-character SHA and use confirmation `APPLY_ENGINE_D1_0012_0013_<sha>`.

1. Confirm account Charliekant and ENGINE_IDEMPOTENCY binding DB ID. The gate exports the complete schema and data before mutation and uploads it as a GitHub Actions artifact for **7 days**. Artifact access follows repository Actions permissions; the dump contains database data and must not be put in logs, PRs, or public storage. Confirm it is downloadable and preserve it in approved secure backup storage if recovery could exceed the retention period.
2. Immediately before apply, the gate rechecks 0009–0011 EXACT, 0012/0013 MISSING, runs=0 and no inbound references. It saves current row counts of all existing tables. It applies only 0012, then 0013.
3. 0013 is sent as one D1 query request: first statement checks for a run row and raises SQLite integer overflow if one exists; all following statements perform the rebuild. Cloudflare documents that the REST query executes semicolon-separated statements as a batch and that a batch is a transaction rolled back on statement failure:
   - https://developers.cloudflare.com/api/resources/d1/subresources/database/methods/query/
   - https://developers.cloudflare.com/d1/worker-api/d1-database/#batch
   The first check and rebuild execute within that batch, closing the gap between the earlier preflight and the actual rebuild. D1 does not support disabling foreign-key enforcement inside a transaction, so the 0013 payload removes the original ON/OFF pragmas after verifying their expected presence. The precheck rejects inbound references. If the REST endpoint does not honor the documented batch atomicity in the target environment, stop and arrange a separately authorized Engine write pause; do not rely on the guard.
4. On success the gate requires all five migrations EXACT, expected indexes and unchanged counts for every table that existed before apply. Counts can change with legitimate concurrent traffic; any mismatch is a failure requiring investigation, not proof of loss or permission to overwrite.

## Failure and recovery

Do not retry blindly after a timeout or failed request: the operation may have committed despite a lost response. Stop further writes with explicit operational authorization, capture readonly schema and counts and preserve the export. 0012 may have completed even when 0013 failed; do not reapply the pair without a new plan.

If 0013 failed atomically, its transaction should roll back and the original 0011 schema remain; verify by readonly classification. If the run table is missing or malformed, and a fresh verified inventory confirms no inbound references and zero affected run rows, the original CREATE TABLE and index SQL are in `apps/padiem-ai-engine/migrations/0011_engine_agent_durable_runs.sql`. Recreate only after explicit CTO authorization and fresh backup; verify schema and row counts after. Never run reconstruction if rows exist without a preservation plan.

For worst-case recovery, download the full export artifact to an access-controlled environment. Cloudflare documents `wrangler d1 execute <database> --remote --file=<export.sql>` for SQL import (https://developers.cloudflare.com/d1/best-practices/import-export-data/). First import into a separate newly provisioned recovery database and verify schema, counts and integrity; the export uses CREATE/INSERT and is not an automatic overwrite of the existing production database. Plan the restore or cutover, including data written since export, with explicit CTO authorization before any production mutation. Time Travel may be another recovery option; assess its recovery point and any newer writes before a restore.
