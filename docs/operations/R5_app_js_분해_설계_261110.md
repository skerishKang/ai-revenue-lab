읽는 법과 주의:

- "최상위 코드"는 주석을 뺀 줄 수다(주석 포함 합계는 903).

### 1.6 순환 의존

- **큰 순환 덩어리 1개**: 22마디(이미 분리된 모듈 6개 + 구역 16개)가 호출로 서로 닿는다.
- **작은 순환 1개**: 달력 모듈 ↔ 앱 연결 구역.
- **순환 밖 6개**: 초기화(부르기만 함), 자동화, 실행 목록 읽기, 보내기·입력창(부르기만 함), 로컬 PC 연결 패널, 최근 대화 메뉴 연결.
- **직접 맞물린 쌍(서로 부름)**: 로그인 연결 코드 ↔ M:auth, 안드로이드 ↔ M:auth, 프로젝트 ↔ M:conversation, 프로젝트 ↔ 오류, 첨부 읽기 ↔ M:conversation, 저장 대화 열기 ↔ M:history, 실행 기록 카드 ↔ M:history, 오류 ↔ M:streaming, 오류 ↔ M:conversation, 실행 기록 카드 ↔ Claw 수동, 저장 대화 열기 ↔ PC 실행, 저장 대화 열기 ↔ Claw 화면 열기, M:settings ↔ 설정 연결 코드, M:conversation ↔ Claw 수동, Claw 공통 ↔ Claw 수동, 공용 도우미 ↔ M:conversation, M:calendar ↔ 앱 연결.

해석: 이 순환은 모두 "함수가 실행될 때" 생기는 호출이다. 모듈은 deps를 호출 시점에 읽으므로 파일 로드 순서 문제는 없다. 설계에 주는 제약은 둘이다.

1. 모듈의 `create()`는 다른 모듈의 함수를 부르지 않는다(선언과 함수 정의만 한다). 이 조건이 깨지면 순환이 로드 시점 문제로 바뀐다.
2. 맞물린 쌍 가운데 같은 책임인 것은 최종 구조에서 한 묶음으로 둔다: 로그인 연결 코드 → auth 계열, Claw 공통 → Claw 계열, 실행 기록 카드 + history의 실행 목록 함수 → 실행 기록 모듈, 설정 연결 코드 → settings 모듈.

### 2.2 app.js에 남길 것

최종 app.js(≈300줄)의 내용은 네 가지뿐이다.

1. **모듈 생성**: 공유 문맥을 만들고 모듈을 정해진 순서로 만든다. 순서는 지금 app.js의 선언 순서를 따른다(요소를 만들어 붙이는 블록의 순서 보존).
2. **연결 호출**: 각 모듈의 `wire()`를 지금의 최상위 리스너 블록 순서대로 부른다.
3. **초기화 순서**: 지금의 4890줄, 5140–5176줄, 6067–6104줄에 있는 호출을 같은 순서로 둔다(`PadiemChatSession.bind`·`PadiemClawSession.bind`, 주소 복원, `automationDestinationReady = true`).
4. **보안 감사가 파일을 고정한 저장소 접근**: `readStoredAndroidHandoff`·`storeAndroidHandoff`·`resumeAndroidHandoff`와 5157줄(§5 D-3에서 달리 정하지 않는 한).

모양(설명용, 구현 아님):

```js
(() => {
  "use strict";
  const app = window.PadiemChatAppContext.create();          // 공유 상태·공유 DOM·등록부
  const use = (factory) => app.provide(factory.create(app)); // 모듈 API를 app에 등록
  const core = use(window.PadiemChatCoreModule);
  const nav = use(window.PadiemChatNavModule);
  // … 나머지 모듈(지금의 선언 순서)
  entry.wire(); projects.wire(); auth.wire(); /* … 지금의 리스너 블록 순서 */
  // 초기화: 지금의 5140–5176, 6067–6104와 같은 순서
})();
```

### 2.3 전역 상태를 모을 곳

- **한 모듈만 쓰는 선언 293개(616줄)** → 그 모듈의 `create()` 안. 예: 자동화의 DOM 참조 41개와 `let` 4개, auth의 74개.
- **둘 이상이 쓰는 78개(147줄)** → `chat-app-context.js` 한 파일. 바뀌는 상태는 읽기·쓰기 접근자 한 쌍으로 정의해 "어디서 바뀌는지"를 한 곳에서 찾게 한다. §1.7의 `activeProject`(5곳이 씀)처럼 쓰는 곳이 많은 상태가 여기서 드러난다.
- **초기화만 쓰는 3개**(`exampleOnLoad`·`resetLinkOnLoad`·`requestedRouteHash`) → app.js.
- 공유 문맥은 지금의 클로저와 같은 "한 겹 이름 공간"이다. 지금도 모든 이름이 한 클로저 안에서 서로 겹치지 않으므로 이름 충돌이 새로 생기지 않는다. 등록할 때 같은 이름이 두 번 들어오면 예외가 나게 만든다.
- 모듈 본문의 `deps.이름` 표기는 바꾸지 않는다. 바뀌는 것은 `deps`를 채우는 방법뿐이다(지금: app.js의 getter 목록 → 최종: 공유 문맥 + 모듈이 등록한 API).

### 2.4 규칙

**1부(A 단계)는 기존 §8 규칙을 그대로 쓴다.** 요약:

- 새 모듈은 전역 공장 하나 `window.PadiemChat<X>Module = { create(deps) { … } }`를 내놓고, `index.html`에서 app.js보다 먼저 로드한다.
- app.js에는 같은 이름의 한 줄 전달 함수를 남긴다(`async`는 `async function` 유지).
- `deps`는 클로저 이름을 읽는 getter(다시 대입하는 상태는 setter 추가). 옮긴 본문은 `x` → `deps.x`만 바뀐다. 옮긴 함수끼리의 호출도 deps를 거친다.
- 선언과 최상위 리스너 등록은 app.js에 남긴다.
- 동작·문구·디자인 변경 0. 이름·DOM id·저장 키·이벤트 이름 유지. PR당 구역 1~2개.

**2부(B 단계)는 규칙 보강 4가지가 필요하다(§5 D-1).**

- **보강 1 — 모듈이 자기 선언을 갖는다.** 한 모듈(함수와 그 모듈의 리스너 등록)만 쓰는 선언을 `create()` 안으로 옮긴다. 조건: (가) 모듈을 app.js의 원래 선언 자리에서 바로 만든다(조회·생성 시점 보존), (나) `create()`는 deps를 읽지 않는다, (다) 요소를 만들어 붙이는 블록은 블록째 옮긴다, (라) 둘 이상이 쓰는 선언은 옮기지 않고 보강 3으로 보낸다. 선례: `chat-calendar-module.js`는 이미 `create()` 안에 상수 4개를 갖고 있다.
- **보강 2 — 리스너 등록을 모듈의 `wire()`로.** 기존 문서 §9가 리스너를 app.js에 남긴 이유는 "모듈이 첫 호출 때 만들어져 등록 시점이 달라지기 때문"이다. app.js가 원래 블록 자리에서 `wire()`를 직접 부르면 등록 시점과 순서가 그대로다. §1.8의 "같은 대상·같은 이벤트" 목록에 걸리는 블록은 합치지 않고 원래 자리에서 따로 부른다.
- **보강 3 — 공유 상태는 한 파일.** §2.3.
- **보강 4 — 전달 함수 대신 모듈 등록부.** 모든 모듈이 같은 공유 문맥을 `deps`로 받고, 각 모듈이 돌려준 API를 문맥에 등록한다. app.js의 모듈 연결부와 전달 함수가 없어진다.

보강 1·2는 구역 하나씩 적용할 수 있다. 보강 3·4는 마지막에 한 번씩 적용한다(B6, B7).
